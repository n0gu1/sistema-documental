# Auditoría 06: reportes y respaldos

Fecha: 7 de septiembre de 2026. Referencia de alcance: `AUDITORIA_MAPA_SISTEMA.md`.
Web: https://sistema-documental-nw05.onrender.com/.

## Alcance y método

Se revisaron exclusivamente reportes del sistema, documentos, versiones, actividad y trazabilidad; creación de respaldos de datos/archivos y recuperación. Se siguieron los componentes indicados por el mapa, sus rutas, controladores, generadores, almacenamiento y comandos programados. Se consultaron únicamente los auxiliares necesarios para comprobar estos flujos.

Se contrastó la API desplegada con las cuentas de prueba administrador, editor y revisor. Se consultaron reportes, programaciones y respaldos existentes; se intentó descargar las dos copias listadas y validarlas mediante `mode=verify`. Este modo no solicita restauración de DB ni archivos. Se cerraron las sesiones utilizadas.

No se generaron nuevas copias ni reportes, no se cambió la configuración ni se ejecutó `mode=restore`, `restore_files` o el botón de prueba de recuperación. La creación de copias puede activar además la purga de respaldos vencidos; la restauración modifica datos existentes. Esta auditoría no necesitó ejecutar esas operaciones sobre producción. Las consultas y verificaciones pueden generar eventos de auditoría. No se modificó código; únicamente se creó este informe.

La interfaz se siguió mediante código fuente, sin validación visual en navegador. **Verificado web** acredita una respuesta observada; **solo código** acredita implementación local, no funcionamiento desplegado. **Falla web** identifica una operación que falló durante la revisión. Los metadatos históricos no prueban que el archivo exista actualmente ni que su contenido sea recuperable. No se certifica identidad entre revisión local y versión desplegada, y no se tuvo acceso a logs del servidor ni al panel de Render.

## Dictamen

Los reportes consultan modelos reales, pero los alcances ejecutivo y editor fallan con HTTP 500. El alcance revisor responde sin filas para la cuenta de prueba. No se encontraron series numéricas de demostración en los generadores y componentes examinados; sí hay valores iniciales vacíos y objetivos de recuperación hardcodeados.

El respaldo tiene un proceso real de serialización, empaquetado, cifrado y almacenamiento en el código. Sin embargo, las dos copias listadas en producción no pudieron descargarse ni validarse: ambas operaciones devolvieron HTTP 500. Por ello no se certifica un respaldo operativo ni una recuperación exitosa. Ambas copias declaran cero archivos. La restauración local combina registros mediante UPSERT sobre un esquema existente; no reconstruye automáticamente una base vacía ni devuelve todo el sistema a un instante exacto.

## Qué impide cerrar la validación

1. Resolver el fallo de reportes ejecutivo/editor y cotejar un archivo exportado contra datos conocidos.
2. Resolver descarga/validación de las copias existentes y obtener una copia actual con manifiesto e inventario verificables.
3. Confirmar ejecución del cron y alertar por la programación vencida.
4. Realizar restauración en un entorno aislado que incluya usuarios, roles, permisos, documentos, versiones, archivos y bitácora; comprobar acceso y contenido después de recuperar.
5. Distinguir copia parcial, contenedor válido y sistema recuperado. Documentar que el restaurador actual hace UPSERT y requiere esquema preexistente.

No se introdujeron correcciones. Se preservaron los cambios preexistentes del espacio de trabajo.
